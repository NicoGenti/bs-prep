## Purpose

BS Prep is an offline-first, dependency-free web application for preparing for a Software Engineer
selection process. It combines structured study content, spaced repetition, quizzes, technical
English practice, and optional GitHub Gist synchronization. It runs entirely in the browser with no
runtime framework and no backend required for the core study features.

## Users and Use Cases

- Single end user preparing for a selection process; the app is the sole interface.
- Core workflows observed in code: browse and complete lessons; take quizzes; build and review an
  SM-2 spaced-repetition deck; practise technical English (exercises and speaking prompts); work on
  CV/cover-letter/references sections; run procedural problem-solving practice.
- Optional workflow: sign in with GitHub and back up/restore progress into a private Gist.
- The application must remain usable with no network access; external links open only on demand.

## Constraints

- No build step: the site is served as-is (plain HTML, CSS, classic scripts).
- No runtime npm dependencies for the application; the repository declares no `dependencies` or
  `devDependencies`.
- No framework, no bundler, no transpiler, no module loader: scripts are classic `<script>` tags.
- Static hosting on GitHub Pages (deployment copies files into `_site/` and publishes them).
- Edge runtime limited to a single Cloudflare Worker used only for the GitHub OAuth code exchange.
- Local persistence is browser `localStorage` only.
- Node.js >= 18 is required for the tooling and tests (`package.json` `engines`).
- Content Security Policy is declared inline in `index.html` and restricts script, connection,
  frame, object and base-URI sources.
- Secrets are never committed: `GITHUB_CLIENT_SECRET` lives as a Worker secret; CI uses
  `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` / `LLM_API_KEY` repository secrets. Only the
  public GitHub OAuth client id is stored in the repository.

## Architectural Style

Static single-page application, "classic scripts + global namespace" style:

- Each browser module is an IIFE that publishes exactly one global namespace object
  (`window.BS`, `window.BSMerge`, `window.BSSanitize`, `window.BSSync`, `window.GEN`, `window.GEN_LABELS`).
- Content files (`data-*.js`) publish data-only globals (`window.LESSONS`, `window.QUIZ`,
  `window.TOPICS`, `window.SECTIONS`, `window.EN_*`, `window.CHECKLISTS`, `window.BULLET_EX`,
  `window.SD_PROMPTS`, `window.PY_EX`, `window.ALGO_TOPICS`, `window.BEHAV_Q`, `window.TRAITS`).
- Navigation is a hash-based router: `location.hash` drives `route()`, which clears the container
  `#app` and calls the registered route function.
- Views are registered by assigning into `window.BS.ROUTES`; `app.js` owns the shared state object
  and is the only module that publishes it.
- The single server-side component is a stateless edge Worker (module export with a default
  `{ fetch }` handler) that performs the OAuth code→token exchange and stores nothing.

### Styling layers (`web-theme` token contract)

Styling is organised as three layers, ordered `theme → bridge → app`:

- **Layer 1 — Theme.** A verbatim copy of `web-kit/skills/web-theme/themes/petalo/` into a repository
  folder (target `assets/theme/`). These files are never hand-edited. The palette is changed only by
  adding a NEW theme folder, or by a brand override (DR-15).
- **Layer 2 — Bridge.** At most ONE alias block mapping this application's existing variable names
  onto `--ui-*` (`--bg: var(--ui-bg)`, `--ink: var(--ui-ink)`, …). The bridge defines no new palette
  value, and it is the ONLY place where aliases may live (DR-14).
- **Layer 3 — App.** `styles.css` and `mobile-glass.css`. They compose tokens; they never redefine a
  `--ui-*` name.

**Capability exception.** bs-prep remains a vanilla static single-page application and does NOT adopt
the Astro/Angular web-kit stacks. `DR-UI-7` ("one stack per site type") applies with this exception
recorded in the Decision Log; `DR-UI-8` (starter-first) is not applied retroactively; `DR-UI-9`,
`DR-UI-10` and `DR-UI-11` do not apply to this repository.

## Module Boundaries

Observed load order in `index.html` — this order *is* the dependency direction:

1. `theme-boot.js` — applies the persisted/system theme before first paint. No dependencies.
2. `sync-config.js` — publishes `window.BS_SYNC` (public OAuth client id and Worker origin).
3. `sync-merge.js` — pure progress-merge/sanitize helpers; publishes `window.BSMerge`.
4. `html-sanitize.js` — strict HTML allowlist sanitizer; publishes `window.BSSanitize`.
5. `data-lessons.js`, `data-quiz.js`, `data-english.js`, `content-meta.js` — content data only.
6. `generators.js` — procedural problem-solving generators; publishes `window.GEN`, `window.GEN_LABELS`.
7. `app.js` — owns state, persistence, SRS/mastery, router; publishes `window.BS`.
8. `sync.js` — optional GitHub login/Gist sync; depends on `window.BS` and `window.BSMerge`;
   publishes `window.BSSync`.
9. `views-core.js` — home / review / course / lesson / settings routes.
10. `views-sections.js` — CV / problem-solving / technical / behavioural / references routes.

Boundary rules visible in the code:

- `app.js` must not depend on `views-*`; `views-*` depend on `app.js` through `window.BS` only.
- `sync-merge.js` is a pure module: no I/O, no DOM, no globals beyond `window.BSMerge`.
- `html-sanitize.js` does not use the DOM: it parses with a hand-written tokenizer.
- `data-*.js` files contain data only and are rewritten by `scripts/update-content.mjs`.
- `worker/` is independent of the browser app and is deployed separately.

### Styling boundary rules (TB)

- **TB-1 — Link order.** `assets/theme/petalo/tokens.css` is the FIRST stylesheet, and `theme-boot.js`
  must EXECUTE BEFORE the stylesheets are applied: the `<script src="theme-boot.js">` tag moves above
  the `<link rel="stylesheet">` rows currently at `index.html:16-18`, so that
  `document.documentElement.dataset.theme` is set before first paint.
- **TB-2 — Colour scheme.** Dark mode is declared by `:root[data-theme="dark"]` with
  `color-scheme: dark` inside the copied tokens; app CSS MUST NOT redefine `color-scheme`. The app
  dark blocks (`styles.css:2`, `mobile-glass.css:4`) become thin maps onto `var(--ui-*)`, not
  independent palettes. Unqualified `[data-theme=dark]` selectors are migrated to
  `:root[data-theme="dark"]`.
- **TB-3 — Tabbar ownership.** `mobile-glass.css` is the SOLE owner of the `.tabbar`,
  `.tabbar a::before` and `.tabbar button::before` geometry **across all viewports** (lifted to top
  level by the desktop-tabbar port, but still defined in a single file). The equal-specificity
  duplication that exists today (`styles.css:123,125` vs `mobile-glass.css:5,7`) is the hazard this
  rule removes: no other file may redefine those selectors. The ownership is marked with a comment
  boundary and enforced by a grep-based CI/test check.
- **TB-4 — Frozen class contract.** The JS-toggled classes `open active show ok bad weak has-thumb
  nav-open sheet-open scrolled` and the selectors bound to them are an API consumed from
  `app.js:87,110,118,120-128`. Token adoption MUST NOT rename them; new `.ui-*` classes are additive
  only.
- **TB-5 — Runtime variables.** `--tabbar-h` and `--thumb-h` are layout metrics owned exclusively by
  the `fitBars()` writes in `app.js` (`app.js:122` and its 13 `calc()` consumers). CSS reads them and
  never writes them. They are NOT design tokens and must not be moved into the theme layer.
- **TB-6 — Sync atomicity.** The theme is persisted in `bsprep.v1`, normalised and merged by
  timestamp (`sync-merge.js:95,232-238,299`) and applied on pull (`sync.js:206`). ANY change to theme
  persistence or to its key/normalisation shape must edit `theme-boot.js`, `app.js:164`,
  `views-core.js:102,107`, `sync.js:206` and `sync-merge.js:95,232-238,299` in lockstep within one
  commit.

## Data and Integrations

Local data (browser `localStorage`):

| Key | Content |
|---|---|
| `bsprep.v1` | Main progress store (versioned): theme, lesson completion, checklist ticks, free texts, mastery, SM-2 cards, streak, activity history, quiz/mock histories. |
| `bsprep.oauth` | Optional GitHub session (token, login, gist id, timestamp). |
| `bsprep.oauth.state` | OAuth state nonce, pending the callback. |

External integrations:

- **GitHub OAuth** — authorization code exchanged for a token by the Cloudflare Worker
  (`GET /state`, `POST /token`). Requested scope is `gist` only.
- **GitHub Gist** — a user-owned secret Gist stores the progress file `bs-prep-progress.json`.
  The browser talks to `api.github.com` directly after the exchange.
- **LLM chat-completions API** — used only by `scripts/update-content.mjs` (monthly automation) to
  regenerate the `data-*.js` content files. Not reachable from the browser application.
- **Content Security Policy `connect-src`** — restricted to `'self'`, `https://api.github.com` and
  `https://*.workers.dev`.

Main entities: lesson (`id`, `topic`, `title`, `mins`, `cards`), quiz item (`Q:<topic>:<index>`),
flashcard (`L:<lesson>:<index>`, `EX:<id>`, `SP:<id>`), topic/section, checklist item, free-text
field, streak, activity day, SM-2 card (`ef`, `int`, `reps`, `due`, `n`, `lapses`).

## Non-Functional Requirements

Security (all observable in code and CI):

- Lesson HTML is sanitized with a strict tag/class allowlist before rendering; dangerous elements
  are dropped with their content.
- OAuth state values are HMAC-signed (SHA-256), time-limited (10 minutes), and compared with a
  constant-time digest check.
- The Worker validates the OAuth redirect URI against an explicit HTTPS origin allowlist and
  rejects requests whose `Origin` is not allowed.
- Request bodies are limited (10 KiB) and `content-type: application/json` is required.
- The GitHub access token is never stored or logged by the Worker; only the `gist` scope is
  accepted.
- Merge inputs are sanitized (prototype-key blacklist, depth/size/count limits, numeric clamping).
- CSP forbids inline scripts, framing, object embedding and restricts `base-uri` and `form-action`.
- CI: security regression tests on push/PR, CodeQL (javascript-typescript, `security-extended`
  queries) on push/PR/weekly, Dependabot for npm, `worker/` npm and GitHub Actions.

Reliability / operability (observed):

- The application is fully functional offline; the backend is optional.
- Actions are pinned to commit SHAs in the deployment workflows.
- The monthly content update never pushes to `main`; it opens or updates a pull request and
  validates the generated output before committing.

Performance / quality (observed):

- No build, no runtime dependency, no bundle step — the published artefact is the source tree.
- Static assets are cacheable by GitHub Pages; the Worker responses are sent with `no-store`.

Privacy (observed):

- Progress stays in the browser unless the user opts into Gist synchronization.
- Optional OAuth is opt-in; with no configuration the sync module does nothing.

## Design Rules

> Approved 2026-11-04. Numbering is stable: DR-1…DR-12 keep their original numbers and DR-13…DR-21
> were appended by the `oracle` refinement. `planner` and `code-reviewer` may cite these ids.

- **DR-1 — Sanitize at the render boundary.** Any HTML coming from content files, the LLM update
  script or a remote source must pass through `html-sanitize.js` (`window.BSSanitize`) before it
  reaches `innerHTML`. IF table→card rendering is adopted later, the sanitizer allowlist grows from
  `class`-only to also emit `data-label` on `td` (`html-sanitize.js:52-60,139-146`), and that change
  ships with a `tests/security.test.js` case (DR-21).
- **DR-2 — The sanitizer stays DOM-free.** `html-sanitize.js` parses with its own tokenizer and an
  explicit tag/class allowlist; do not reintroduce `DOMParser` or `innerHTML`-based sanitization.
- **DR-3 — No secret ever enters the repository or the browser bundle.** Secrets are Worker secrets
  or CI repository secrets; the browser only receives the short-lived, `gist`-scoped token.
- **DR-4 — Content identifiers are stable.** SM-2 progress in `localStorage` is keyed by content
  ids (`L:`, `Q:`, `EX:`, `SP:` and lesson ids). Content updates must not remove or renumber
  existing ids.
- **DR-5 — Merge logic stays pure.** `sync-merge.js` performs no I/O and no DOM access; merging is
  deterministic and per-entry last-timestamp-wins. Theme persistence is merged by the same rule and
  therefore follows the lockstep requirement of TB-6: reader, writers, merge normalisation and
  apply-on-pull move together in one commit.
- **DR-6 — No build step and no runtime npm dependency for the browser app.** The browser
  application ships as source; adding a bundler or a runtime npm dependency changes the deployment
  contract. Adopted theme assets are copied static files served from `'self'`; if a web font is ever
  added it is a vendored WOFF2 declared with `@font-face`, NOT an `@fontsource` npm package. The
  current decision (d) keeps the system font stack, so this clause is preparatory.
- **DR-7 — The Worker remains stateless.** It may issue and validate OAuth state and perform the
  code exchange; it must not persist, cache or log tokens.
- **DR-8 — The CSP is not weakened.** Inline scripts, `unsafe-eval`, framing and `object-src` stay
  disallowed unless a decision is recorded in the Decision Log. `font-src 'self'`
  (`index.html:14`) is the operative constraint for any web font adopted later; `style-src` keeps
  `'self' 'unsafe-inline'`, which the JS-driven inline styles currently rely on.
- **DR-9 — Scripts keep their global contract.** Each browser module publishes its documented
  namespace and consumes others only through those namespaces; load order in `index.html` is
  preserved when modules are added. TB-1 is the single sanctioned ordering change.
- **DR-10 — The Worker deployment is conditional.** Deployment must degrade gracefully when the
  Cloudflare secrets are absent, exactly as the current workflow does.
- **DR-11 — Content changes go through review.** The monthly automation validates, sanitizes and
  proposes changes via pull request; it never merges into `main` by itself.
- **DR-12 — New behaviour is covered by the security regression suite.** Security-relevant changes
  to the sanitizer, the merge logic or the Worker are covered by `npm test`.
- **DR-13 — Token source of truth.** Colour, radius, shadow, spacing, typography and duration values
  exist only as `var(--ui-*)` or through a bridge alias (DR-14). Documented exceptions: device insets
  (`env(safe-area-inset-*)`), fixed icon stroke widths, and runtime-derived values — the runtime
  allowlist is progress-bar width %, the drag transform, and the `fitBars()` variables of TB-5. The
  remaining hex/rgba/px/shadow/duration literals in `styles.css` and `mobile-glass.css` (7 outside
  tokens today) are a bounded audit backlog, not licence for new ones. Gate: an adapted
  `audit-theme.sh`-style check over `styles.css` + `mobile-glass.css` reporting zero new violations.
- **DR-14 — No second design system.** Application variable names are aliases (`--bg: var(--ui-bg)`),
  and the alias block is the only place they may be defined. No `--ui-*` name is redefined outside
  the copied theme folder or the brand override file.
- **DR-15 — Theme files are verbatim.** A palette change is a NEW theme folder, or `assets/brand.css`
  produced by the `web-brand` skill and verified with its `contrast.py`. Editing `petalo/tokens.css`
  in place is forbidden; the copy tracked here must stay byte-identical to the skill's source.
- **DR-16 — Motion stays cheap and tokenised.** 150–400 ms via `--ui-dur-*`; animate only `transform`
  and `opacity`; `transition: all` (implicit or explicit) and `transition: font-size` are disallowed
  (`styles.css:80,95,114` — one layout-property transition and two implicit `transition: all`).
  Easings come from `var(--ui-ease-*)` (`styles.css:137`, `mobile-glass.css:24`). The reduced-motion
  blocks stay complete (`styles.css:178-181`, `mobile-glass.css:32-35`), and no new `@keyframes` is
  added without a reduced-motion counterpart.
- **DR-17 — Focus and touch targets.** Interactive targets stay at least 44 px (`--hit`,
  `styles.css:160-165` stays as-is). Focus visibility comes from `--ui-focus`; today the ring is
  hard-linked to `--accent` (`styles.css:10`), so removing the dead `--focus` token must first wire
  focus styling to `var(--ui-focus)`.
- **DR-18 — Mobile tables are deferred.** Decision (c) = later. App-rendered tables
  (`views-core.js:85`, `views-sections.js:32,88`) are targeted in a future UI pass; lesson/content
  tables wait for generator support, because the sanitizer emits only `class`. Interim behaviour is
  the existing horizontal scroll (`styles.css:172-173`). The breakpoints 767/768 px width and
  950 × 500 px height are a documented exception to the skill's 760 px. The 767/768 px width and
  950 × 500 px height breakpoints (and the `min-width: 768px and min-height: 501px` desktop-lock at
  styles.css:101-105) also govern the desktop bottom tabbar geometry introduced by the
  desktop-tabbar port: desktop density applies at/above 768 px and is unaffected by the height
  exception.
- **DR-19 — Dead code is removed only in the tokens pass.** The zero-reference tokens `--radius-md`,
  `--text-xl`, `--focus` and `--shadow` are removed during that pass only, and each must be re-grepped
  immediately before deletion: the audit claimed them dead but `--shadow` was not re-verified.
- **DR-20 — UI change gate.** `npm test` green plus screenshots at 1440 and 390 in `docs/screens/`,
  named `<route>-<width>.png`, before merge. Current state: only 1280/780/1400 exist, in `docs/`.
- **DR-21 — Sanitizer hygiene.** Any change to the sanitizer allowlist ships with a case in
  `tests/security.test.js` in the same change.

## UI & Delivery

> bs-prep is a token-contract adopter of web-theme (see DR-13…DR-21), not a web-kit site stack
> adopter. The facts below are observations from the current code.

Observed delivery and UI facts:

- Deliverable: a static, installable PWA (`manifest.webmanifest`, `display: standalone`), published
  by GitHub Pages on every push to `main`; the OAuth helper is published separately to Cloudflare
  Workers.
- The application shell is `index.html` (100 lines): two stylesheets (`styles.css`,
  `mobile-glass.css`), a manifest link, an inline CSP, and thirteen ordered classic scripts.
- Theming: light/dark driven by `document.documentElement.dataset.theme`; the choice is persisted in
  the progress store and applied pre-paint by `theme-boot.js`; the system colour scheme is the
  fallback.
- Layout: a single bottom tab bar (5 direct tabs + "Altro" More sheet) on every viewport; side
  navigation and `#menuBtn` retired on desktop; bottom sheet + draggable sheet handle remain. Media
  queries break at 768 px width and 950 px × 500 px height (DR-18).
- Screenshots of the dashboard, dark theme, mobile and English views live in `docs/`.
- Accessibility signals present in the code: `aria-*` attributes on progress bars and tab state,
  `aria-label` on icon buttons, keyboard handling for `Escape` and `Tab` focus trapping in the
  sheet, visible focus handling delegated to the stylesheet.
- Localised UI copy is Italian; study content is bilingual (Italian lessons, English practice).
